# 音频修复功能优化方案

## Context

音频修复功能（去混响、超分辨率、降噪适配）当前存在三类问题：

1. **算法误用**：`SuperResolutionRestorer` 错误使用 `speechbrain/metricgan-plus-voicebank`（降噪模型）做带宽扩展，非真正的超分辨率；项目已下载的 `MossFormer2_SR_48K`（真正的 BWE 模型）却通过 denoise_adapter 以"降噪算法"身份错误暴露
2. **工程缺陷**：后端绕过项目已有的 `task_queue`，直接用 `threading.Thread` 跑修复任务，无法统一限流；进度仅 5 档百分比无步骤文本；`upload-batch` 漏写 `user` 字段导致任务不可见
3. **体验问题**：前端轮询刷新时已展开的波形对比面板丢失（canvas 无法通过 innerHTML 序列化）；错误被静默吞掉；无拖拽上传；无步骤化进度反馈

优化目标：用已下载的 `MossFormer2_SR_48K` 替换误用的 MetricGAN+，接入 `task_queue` + WebSocket 步骤化进度，修复前端波形重渲染 bug 并补齐拖拽/错误反馈等体验短板。**无需下载新模型**——所需模型已全部就位。

## 关键决策

| 决策点 | 方案 | 理由 |
|---|---|---|
| task_queue 集成 | 创建独立 `restoration_task_queue = TaskQueue(max_workers=1)` | 隔离 MOS 与 restoration，避免超分长音频阻塞 MOS 评分；4090 24GB 显存可容纳并发模型 |
| WebSocket 管理 | 提取 `ConnectionManager` 到 `backend/app/core/websocket.py` 共享 | 该类完全通用，提取是零行为变更重构；mos.py 与 restoration.py 各持独立实例 |
| 任务持久化 | 保持与 MOS 一致（无持久化） | 持久化是跨模块横切关注点，单给 restoration 加 SQLite 会制造技术债；任务短生命周期可接受重启丢失 |
| 超分辨率算法 | 重写 `SuperResolutionRestorer` 用 ClearVoice `MossFormer2_SR_48K` | 真正的 BWE 模型（MossFormer2+HiFiGAN），支持 8k/16k/24k/32k→48k，已下载 |
| 去混响算法 | 保留 SepFormer WHAMR 8kHz + 暴露 `DereverbWienerRestorer` | 8kHz 是模型硬约束；Wiener 变体已实现未暴露，给用户无模型快速选项 |
| SR_48K 重复暴露 | 从 `_DENOISER_SR_CONFIG` 移除 `clearvoice_mossformer2_sr_48k` | 它是 BWE 模型非降噪器，当前通过 denoise_adapter 暴露属语义错误，且与原生超分重复 |
| 波形重渲染 bug | 已展开面板打 `data-compare-expanded` 标记，重渲染时跳过该 item 的 outerHTML 替换 | 保留 canvas+audio 活动状态，避免序列化问题 |
| 多算法对比功能 | 延后 | 工作量等于一个独立特性，应与降噪测评模块统一规划 |

## 分阶段实施

### Phase 1：算法层修正（算法质量）

**文件**：
- `app/algorithms/restoration/super_resolution.py`
- `app/algorithms/restoration/dereverberation.py`
- `app/algorithms/restoration/__init__.py`

**改动**：
1. **重写 `SuperResolutionRestorer`**：删除 MetricGAN+ 误用与多项式回退；改用 ClearVoice `task="speech_super_resolution"`, `model_name="MossFormer2_SR_48K"`。复用 `clearervoice_denoiser.py` 的集成模式：`CLEARVOICE_MODEL_SPECS["clearvoice_mossformer2_sr_48k"]` 配置 + monkey patch 本地加载 + 临时文件推理 + `_parse_output` + 音量归一化。可直接 import `ClearVoiceWrapperDenoiser` 并委托调用，或继承复用其 `initialize`/`_parse_output` 逻辑。
2. **暴露 `DereverbWienerRestorer`**：在 `__init__.py` 的 `get_available_restorers()` 中添加 `dereverberation_wiener` 条目，并在 `RESTORATION_DESCRIPTIONS` 补充描述（传统方法、无模型、快速、无重采样）。
3. **清理 `_DENOISER_SR_CONFIG`**：移除 `clearvoice_mossformer2_sr_48k`（语义错误，BWE 不应作为降噪器暴露）；采样率改为从 `CLEARVOICE_MODEL_SPECS` 读取，单一数据源。
4. **统一描述字段**：`RESTORATION_DESCRIPTIONS` 的 `advantages/limitations` 与 `DENOISER_DESCRIPTIONS` 的 `pros/cons` 字段名对齐（统一为 `advantages/limitations`，前端适配）。
5. **修复 supported_formats 不一致**：`config/config.yaml` 的 `audio.supported_formats` 补充 `.flac`（与前端 `accept=".wav,.mp3,.flac"` 一致）。

### Phase 2：后端工程化

**文件**：
- 新建 `backend/app/core/websocket.py`
- `backend/app/api/restoration.py`（重写异步处理）
- `backend/app/api/mos.py`（导入提取后的 ConnectionManager）
- `backend/app/main.py`（lifespan 启动 restoration 队列）

**改动**：
1. **提取 ConnectionManager**：把 `mos.py` 中的 `ConnectionManager` 类原样迁移到 `backend/app/core/websocket.py`；`mos.py` 改为 `from app.core.websocket import ConnectionManager`。
2. **restoration 队列接入**：
   - 在 `restoration.py` 顶部创建 `restoration_task_queue = TaskQueue(max_workers=1)` 和 `restoration_manager = ConnectionManager()` 实例
   - 保留 `restoration_tasks` 本地 dict 作为 API 层状态源（对齐 MOS 模式），task_queue 用于执行调度
   - 写 `async def process_restoration_task(queue_task)` processor：从 `queue_task.data` 取 `algorithm/filename/file_path`，用 `loop.run_in_executor` 跑同步 `restorer.restore`，更新 task_queue + 本地 dict + WebSocket
   - `main.py` lifespan 中 `await restoration_task_queue.start(process_restoration_task)`，关闭时 `await restoration_task_queue.stop()`
3. **步骤化进度**：定义 `RESTORATION_PROGRESS_STEPS`：
   ```
   0   → queued    → [queued]等待处理...
   10  → loading   → [loading]正在加载算法模型...
   30  → reading   → [reading]正在读取音频文件...
   50  → processing→ [processing]正在执行音频修复...
   80  → saving    → [saving]正在保存修复结果...
   100 → done      → [done]处理完成
   ```
   processor 各阶段调用 `restoration_task_queue.update_task()` + `restoration_manager.send_progress()`。注意 `Task.progress` 是 `int`，用整数百分比。
4. **WebSocket 端点**：`@router.websocket("/ws/{task_id}")`（完整路径 `/restoration/ws/{task_id}`），accept 后每秒推送 `{status, progress, message, step}`。
5. **修复 upload-batch bug**：L424 `task_info.dict()` 后补 `task_dict["user"] = current_user.username`。
6. **保留 `_restorer_instances` 缓存**与 `init_restoration()` 预加载逻辑，processor 通过 `_get_restorer(name)` 获取实例。
7. **`process/{task_id}` 端点**：构造 `Task(data={algorithm, filename, file_path})` 后 `await restoration_task_queue.submit(task)`，不再直接 `threading.Thread`。

### Phase 3：前端体验

**文件**：
- `frontend/static/js/app.js`（L836-1067 restoration 段）
- `frontend/static/index.html`（L220-270 restoration Tab）
- `frontend/static/css/app.css`（步骤进度样式）

**改动**：
1. **修复波形重渲染 bug**：`renderRestorationTasks` 重渲染前，给已展开对比面板的 task-item 打 `data-compare-expanded="true"`；重渲染时对该 item 跳过 `innerHTML` 替换，仅原地 patch 状态徽章和进度条宽度。
2. **步骤化进度显示**：新增 `restorationStepNames` 映射（对齐 `mosStepNames` 模式），进度条下方显示当前步骤文本。
3. **错误反馈**：L846/932 的 `catch (_) {}` 改为 `catch (err) { console.warn(...); showToast('加载失败: '+err.message, 'error'); }`。
4. **上传体验**：
   - 上传后清空 `fileInput.value`，允许重复选同一文件
   - 为 `restoration-upload-zone` 绑定 dragover/drop 事件，支持拖拽上传
   - 文件大小预校验（对齐 `config.audio.max_file_size`）
5. **删除死代码**：移除 `state.restorationPollTimer`（L220）。
6. **WebSocket 接入**（可选增强）：复用 MOS 的 WebSocket 连接模式，restoration 任务也实时推送进度，减少轮询压力。若时间紧可保留轮询。
7. **音频播放优化**：试听对比的 `?token=` URL 改为 fetch 后用 `URL.createObjectURL`（对齐 `downloadRestorationResult` 模式），避免 token 泄漏到日志。

## 验证方案

1. **算法层**：
   - 启动服务，`GET /api/restoration/algorithms` 确认包含 `super_resolution`（新实现）、`dereverberation`、`dereverberation_wiener`，且不再有 `clearvoice_mossformer2_sr_48k`（作为降噪器）
   - 用 `data/test_audio/noisy_white_-5db.wav` 测试超分辨率：输入 16kHz，输出应为 48kHz，高频有恢复
   - 测试 `dereverberation_wiener`：无模型加载，快速完成
2. **后端**：
   - 提交修复任务，观察日志确认走 `restoration_task_queue` 而非 `threading.Thread`
   - WebSocket 连接 `/api/restoration/ws/{task_id}`，确认收到步骤化进度消息
   - `upload-batch` 后 `GET /tasks` 确认批量任务可见且可删除
   - 同时提交 MOS 和 restoration 任务，确认互不阻塞
3. **前端**：
   - 提交任务后展开试听对比，等待轮询刷新，确认波形不消失
   - 拖拽文件到上传区，确认可上传
   - 错误场景（如断网）确认有 toast 提示
   - 进度条下方确认显示步骤文本
4. **回归**：MOS 评分功能不受影响（ConnectionManager 提取后 mos.py 导入正常）

## 已知限制（记录于工作记录）

- 去混响 SepFormer WHAMR 强制 8kHz，重采样回原采样率有音质损失（模型硬约束）
- 任务状态无持久化，服务重启丢失（与 MOS 一致，待跨模块统一处理）
- 多算法横向对比功能延后（应与降噪测评模块统一规划）
